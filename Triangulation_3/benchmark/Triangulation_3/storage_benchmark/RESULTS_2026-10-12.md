# Results and analysis, 2026-10-12

Machine: 2-core Intel Xeon @ 2.8 GHz (KVM cloud VM), Ubuntu 24.04, g++ 13.3, CMake Release,
Boost 1.86 (no GMP). Timings on this VM vary by about ±3%; ratios below 5% are within noise.
INDEX and INDEX_EXP were built from HEAD (3722092900e) with `prevent_deref_equality.patch`
(without it, INDEX does not finish, see README). INDEX_EXP adds the experiments of
`indexed_storage_experiments.patch`.

## Summary

* Correctness: all 52 checks are identical for MAIN, HANDLE and INDEX (same Delaunay
  triangulations, same `locate` results, valid, consistent neighbors, copies).
  Removal could not be checked for INDEX (does not compile), and iteration over all cells is
  quadratic with INDEX without the patch (see README).
* Memory: INDEX needs about half the memory (cube 1M: 248 MB vs 503 MB).
* Speed: INDEX is faster for memory-bound work (locate −13%, random-order insertion −6..−15%,
  cell traversal −21%, copy −89%), but **7–12% slower for `insert_range`** (the main use case,
  with spatial sorting) and **~20% slower for `incident_cells`**.
* HANDLE (this branch with pointers) is as fast as or ~5% faster than MAIN, so the refactoring
  of the algorithms to descriptors is not the cause.

## Why `insert_range` is slower

With spatial sorting the working set is cache friendly in all configurations, so the
insertion is bound by instructions, not by memory. callgrind, 200k points:

| | instructions | data reads | D1 misses | LL misses |
|---|---|---|---|---|
| MAIN   | 5.16 G | 1.39 G | 40.6 M | 3.46 M |
| INDEX  | 6.04 G (+17%) | 1.87 G (+35%) | 28.2 M (−30%) | 1.01 M (−71%) |

INDEX wins the cache-miss battle but executes 17% more instructions (+23.5% vs HANDLE). The
predicates are identical (same instruction counts). The extra work is in `Indexed_storage`
(`_insert_in_small_hole`, `find_conflicts`), from these causes:

1. **Generic reset when a cell is recycled** (`Indexed_container::create()` →
   `Property_container::reset()`): a loop over all property arrays with a virtual
   `reset()` each. About 480M instructions (8%) and 5–6% of the time. A reset is needed, but
   only for the conflict flag: cells of large holes (`_insert_in_hole` → `create_star_3` →
   `delete_cells`) are deleted while still marked *in conflict*, and `Compact_container`
   hides that by reconstructing the cell. Skipping the reset entirely breaks the sphere data
   set (`CGAL_error` in `Small_unordered_map::get_and_erase`); clearing only `Cell_data` is
   correct (`CGAL_EXP_NO_RESET`).
2. **Double indirection on each access**: `cell_storage()[ci]` →
   `Property_map::parray_` → `Property_array::data_` → element; the same for points,
   `c:data` and vertices. Caching the base pointers in the TDS (`CGAL_EXP_RAW_PTR`) leaves the
   instruction count unchanged but saves 2–3% of the time (the latency of dependent loads).
3. **`removed_` is a `std::vector<bool>`**: a bit read-modify-write on each create/delete,
   about 1% (`CGAL_EXP_REMOVED_CHAR`).
4. Smaller items: `tds()` goes through `std::unique_ptr` in `Triangulation_3` (~60M
   instructions), and the virtual `push_back`/`pop_back` churn (`remove()` pops the last
   element and the next `create()` pushes it back, ~120M instructions; disabling it saves
   only 0.5%).

Ruled out: aliasing through the `unsigned char` conflict flag (an enum flag gives exactly the
same code, `CGAL_EXP_NO_CHAR_ALIAS`), and the predicates.

With 1+2+3 (INDEX_EXP), `insert_range` goes from +12% to +6.5% vs HANDLE on the cube (and on
par for the sphere and ocean data sets), while keeping the halved memory. The rest is
container bookkeeping (free list, counters, 16-byte handles in the remaining handle-based
code).

## Why `incident_cells` is slower

`TDS::just_incident_cells_3` is still written with handles. With `Index_tag`, each
`c->vertex(i)`/`c->neighbor(i)` builds a proxy `Cell{tds, idx}` and goes
`handle.cont_ → cell_container_.storage_.parray_ → data_ → element`, a chain the compiler
cannot hoist because `cont_` is per-handle data. The output vector also holds 16-byte handles.
A descriptor-based copy of the same loop (1M points, best of 5):

| | handle API (`dt.incident_cells`) | descriptor loop |
|---|---|---|
| HANDLE | 1126 ms | 958 ms |
| INDEX | 1272 ms | 868 ms |
| INDEX + raw pointers | 1238 ms | 787 ms |

So the storage itself is faster here; porting the remaining handle-based TDS functions to
descriptors fixes it.

## Suggested changes

1. Fix `Prevent_deref` equality (`prevent_deref_equality.patch`), and preferably also
   `Index_iterator::operator-`, which is O(n) with garbage despite the random access category.
2. Make `remove()` compile with `Index_tag` (hash of `Index_handle` in
   `Hash_handles_with_or_without_timestamps`).
3. Replace the generic `properties_.reset()` on recycling by resetting only the TDS data
   (and user properties, if any, outside the hot path).
4. Cache the base pointers of the hot arrays (storage, `c:data`, points) in the TDS.
5. Store the removed flag in the element storage (as `Compact_container` does with the
   free-list pointer) or in a byte array instead of `std::vector<bool>`.
6. Port the remaining handle-based TDS functions (`incident_cells_3`, `create_star_3`, ...) to
   descriptors.
